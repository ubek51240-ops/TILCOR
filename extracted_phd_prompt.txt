PROJECT CONTEXT TO VERIFY
The user has reported that the project may already contain an Uzbek–English dictionary database, an English
collocations database, and four PDF books that are intended to represent two English originals and their
corresponding Uzbek translations. Treat this as a lead to verify, not as a fact about the current file system.
Confirm the actual number of books, languages, editions, completeness, page counts, text extraction
quality, and whether each translation genuinely corresponds to its source. If any item is missing or
mismatched, report it; do not substitute another book.
PHASE 0 — READ-ONLY PROJECT AUDIT (DO THIS FIRST AND STOP)
Inspect the repository and produce an audit report without changing files. Include: A. project directory tree
and current app entry points; B. current framework, language, package manager, database, runtime, and
deployment assumptions; C. available dictionary/collocation data, schemas, formats, encodings, duplicates,
missing fields, and sample records (do not expose unnecessary sensitive data); D. inventory of the four
PDFs: filename, probable language, page count, selectable text vs scanned pages, extraction sample, and
pairing confidence; E. current features that actually work, features that are incomplete, and features that are
only ideas; F. technical risks, data-loss risks, licensing/copyright questions, security risks, and
research-validity risks; G. a prioritized roadmap with estimated complexity (not false precision),
dependencies, acceptance criteria, and explicit approval gates; H. exact commands needed to run the
current project and how you verified them. Do not start Phase 1 until the user approves the audit and the
proposed scope. If no codebase is found, say so and propose a minimal architecture; do not pretend an app
already exists.
PHASE 1 — DATA SAFETY AND REPRODUCIBLE FOUNDATION
After approval: - Create a timestamped backup of the project and a manifest of source files; verify the
backup can be read. - Keep raw PDFs and original databases unchanged. Store processed artifacts
separately and record provenance. - Define a documented data model for books, editions, languages, source
pages, paragraphs/segments, alignments, collocation candidates, manual annotations, users/roles if needed,
and review status. - Preserve Unicode accurately, including Uzbek apostrophe variants, o‘/g‘ characters,
Cyrillic if present, punctuation, diacritics, and paragraph boundaries. - Add stable IDs and provenance fields
rather than relying on row numbers or file order. - Use reversible database migrations, validation,
transactions, and clear error messages. - Provide a small synthetic/demo dataset only if needed for testing,
clearly labeled DEMO and never mixed into research data. Acceptance: backup/restore procedure
documented; original data checksums or equivalent integrity checks recorded; schema documented; no
original content altered.
PHASE 2 — PDF EXTRACTION AND TEXT QUALITY CONTROL
Build a repeatable pipeline for extracting text from each PDF: - Detect whether each page has a text layer.
Use OCR only for pages that require it, and report the OCR engine/language assumptions. - Preserve book ID,
edition, language, PDF page, printed page if reliably detectable, paragraph/segment order, extraction
method, and quality flags. - Do not silently merge paragraphs, remove meaningful punctuation, normalize
away apostrophe distinctions, or discard footnotes/headings that may matter to interpretation. - Store raw
extraction separately from normalized searchable text. Make every normalization rule documented and
reversible where feasible. - Detect empty pages, repeated headers/footers, likely OCR corruption, broken
hyphenation, suspicious character substitutions, and duplicated paragraphs. Flag rather than silently “fix”
uncertain cases. - Create a page-by-page preview so a human can compare extracted text against the PDF.
Acceptance: report extraction quality per book and page; compare a stratified manual sample against the
PDF; show known errors and their handling; allow reprocessing without duplicating records.

PHASE 3 — ALIGN THE ENGLISH AND UZBEK TEXTS
Implement sentence/segment alignment that supports one-to-one, one-to-many, many-to-one, and
unmatched segments. Do not assume sentence boundaries map perfectly between languages. - Preserve
the original sequence and links to book/page/paragraph. - Display paired English and Uzbek segments side
by side, with neighboring context. - Provide manual create/edit/split/merge/unlink controls, undo where
feasible, and a review queue for uncertain alignments. - Store alignment method, confidence score if
supported, reviewer, review status, timestamp, and notes. Explain what a confidence score means; do not
present an uncalibrated model score as a probability. - Never auto-approve low-confidence or ambiguous
alignments. Do not fabricate a translation for missing segments. - Support filtering by book, page, language,
alignment status, and reviewer. Acceptance: user can trace any aligned pair back to its source PDF page;
alignment edits persist after refresh/restart; unmatched content remains visible; alignment changes are
logged.
PHASE 4 — COLLOCATION SEARCH AND CONTEXTUAL EVIDENCE
Use the existing English collocation database if it is valid; do not replace it before profiling it. Build
exact/normalized lookup and context-aware matching with transparent rules. - Find candidate collocations in
English source text and show the complete sentence/paragraph, source book/page, and matched span. -
Handle case, punctuation, inflection, spacing, apostrophes, and configurable lemmatization carefully. Keep
the raw surface form and normalized form separately. - Distinguish a collocation dictionary entry from an
occurrence in a text. One entry may have many occurrences; do not collapse or double-count them. - Link
each occurrence to its aligned Uzbek segment(s), but do not assume the linked Uzbek text contains a direct
equivalent. - Mark cases where the collocation is omitted, paraphrased, structurally changed, replaced by a
different image, or not confidently alignable. - Explain the matching method and its limitations. If a POS
tagger, lemmatizer, or NLP model is unavailable or weak for Uzbek, mark it as a limitation and allow manual
review. Acceptance: each result is traceable to context and page; repeated occurrences are handled
correctly; false matches can be rejected; search results can be exported with provenance.
PHASE 5 — RESEARCHER ANNOTATION AND CLASSIFICATION
Provide a configurable annotation interface for the researcher. Do not hard-code a linguistic taxonomy as
universally correct. Allow the researcher to define or revise categories with descriptions and examples, and
preserve previous annotations when categories change. Possible fields include: collocation
headword/lemma, surface form, grammatical pattern, semantic relation, translation strategy, equivalent
type, omission/addition, paraphrase, cultural reference, confidence, evidence note, and reviewer status.
These are candidate fields only; present them for approval before treating them as the study's final coding
scheme. - Support multiple labels when justified, annotation guidelines, notes, disagreements, and
adjudication. - Keep an audit trail of changes and record who changed what and when if user accounts are
implemented. - Separate automatic suggestions from human-confirmed annotations. Acceptance: categories
are configurable; every research label can be traced to an explicit guideline; unreviewed model suggestions
are never presented as verified findings.
PHASE 6 — QUANTITATIVE ANALYSIS WITH TRANSPARENCY
Implement statistical tools only where the required data and assumptions are available. - Report raw counts,
normalized frequency (state the denominator, such as per million tokens), dispersion by text/book, and
number of unique types vs occurrences. - If implementing association measures such as MI or t-score,
document exact formulas, tokenization, window size, frequency thresholds, contingency counts, and edge
cases. Do not calculate or label scores if required counts are missing. - Explain that association scores can
favor different frequency profiles and are not by themselves proof that a sequence is a linguistic collocation.
- Avoid comparing corpora of very different sizes without normalization and context. - Allow reproducible
export of input counts and calculation settings. - Keep source-language and translation-language counts
separate; do not treat translation frequency as directly equivalent without methodological justification.
Acceptance: independently check sample calculations with hand-computable test cases; show formulas and
parameters in the UI or methods documentation; flag low-frequency and unreliable cases.

PHASE 7 — CORPUS SEARCH, KWIC, FILTERS, AND EXPORT
Build a practical research interface with: - bilingual aligned view and sentence/paragraph context; -
keyword-in-context (KWIC) view with configurable left/right context; - search by word, lemma if supported,
collocation, phrase, book, page, language, annotation, and alignment status; - filters for
reviewed/unreviewed, uncertain, omitted/paraphrased/alternative translation where those labels are
approved; - pagination and performance-conscious queries; - export to CSV and Excel with UTF-8-safe Uzbek
characters and stable IDs. Export fields should include, when available: corpus record ID, book/edition ID,
language, English source segment, Uzbek target segment, collocation entry, matched span, surrounding
context, PDF page, printed page if verified, alignment type/status, confidence/method, annotations, reviewer
status, notes, and export timestamp. Do not export fields that do not exist; label missing values clearly.
PHASE 8 — UI, ACCESSIBILITY, SECURITY, AND DEPLOYMENT
Design a clean, professional, research-oriented interface. Prioritize readability and evidence traceability over
decorative effects. - Provide Uzbek and English UI labels where useful; preserve language-specific text and
use readable fonts. - Make tables, long passages, and side-by-side segments usable on desktop and mobile
layouts where technically feasible. - Add loading, empty, success, and actionable error states; keyboard
accessibility; clear navigation; and confirmation before destructive actions. - Protect uploaded files and
research notes. Validate inputs, use parameterized database operations, manage secrets through
environment variables, and avoid exposing credentials or local file paths to ordinary users. - Do not make
the corpus publicly accessible by default. Provide authentication/authorization only after discussing the
simplest appropriate design. - Before deployment, explain hosting requirements, cost, backups, HTTPS, data
access, copyright/licensing, and whether the corpus can legally be shared. Do not publish full copyrighted
books or their extracted text unless permission allows it. - Do not add analytics, external AI APIs, telemetry,
or third-party uploads without disclosure and approval.
PHASE 9 — VALIDATION AND RESEARCH QUALITY ASSURANCE
Create a validation plan and run it. Use the following as a pilot plan, not as a universal scientific standard: -
Manually inspect a stratified sample of extracted pages and segments from each book. - If enough material
is available, create at least 100 manually verified aligned segment pairs for an initial pilot; if not, report the
available sample and limitations. - Build a human-checked reference set of collocation occurrences. Report
precision, recall, and F1 only when true positives, false positives, and false negatives can be reliably
counted. Explain the annotation protocol. - Test boundary cases: punctuation, capitalization, inflection,
repeated collocations, one-to-many alignment, missing translation, duplicate records, OCR errors, Uzbek
apostrophe variants, empty input, and very long text. - Test database integrity, import/export round-trips,
persistence after restart, backup restore, access controls, and failure recovery. - Report actual test results,
sample sizes, failures, and unresolved issues. Never claim “100% accurate” without a defensible exhaustive
evaluation. Acceptance: reproducible test instructions, visible test results, known limitations, and a
prioritized defect list.
PHASE 10 — DOCUMENTATION AND RESEARCH HANDOVER
Deliver: 1. a plain-language Uzbek user guide; 2. installation/run instructions matched to the actual
operating system and project; 3. architecture diagram and data-flow description; 4. database schema/data
dictionary; 5. PDF extraction and alignment methodology; 6. annotation guideline template; 7. formulas and
settings for quantitative measures; 8. testing and validation report; 9. backup/restore and troubleshooting
guide; 10. limitations and future-work list; 11. a reproducible example from PDF page to extracted segment,
aligned pair, collocation occurrence, annotation, and exported row. The application may support Chapter II
and Chapter III analyses, but do not automatically write thesis conclusions or invent citations. Any generated
prose must distinguish measured results, cited theory, researcher interpretation, and unverified hypotheses.
